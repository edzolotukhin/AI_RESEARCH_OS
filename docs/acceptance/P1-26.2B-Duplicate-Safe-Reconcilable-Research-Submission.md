# P1-26.2B — Duplicate-Safe, Reconciliable Research Submission

## Verdict

PROPERTY AD is accepted offline. A logical UI form action now has a stable UUID4 submission key, an owner-scoped deterministic Project identity, and one atomically elected durable `research_submissions` record before Planner begins. Replays reconcile; they never re-enter Planner or create another WorkflowRun.

## Forensic root cause

Previously the UI created and committed a random Project, then blocked synchronously in Planner, while passing `idempotency_key=None`. Client timeouts were ambiguous, `research_submissions` was empty by design, and every retry created another Project and paid run.

## Old write boundary

```text
POST /ui/research
  -> random Project commit
  -> synchronous Planner
  -> Project/template/run commits
  -> 303 /ui/research/{run_id}
```

No durable client-known receipt existed before Planner.

## New idempotency boundary

```text
GET /ui/research/new
  -> opaque UUID4 submission_key in form

POST /ui/research (same key for one logical action)
  -> validate UUID4
  -> derive UUID5 Project ID from principal + key
  -> create-or-load that Project
  -> atomic research_submissions.try_register(project_id, key, fingerprint, reserved_run_id)
      winner -> synchronous Planner -> exactly one WorkflowRun using reserved_run_id
      replay -> reconciliation status only; no Planner
  -> redirect to Research when run exists
     or /ui/research/submissions/{key} while pending
```

The database `ON CONFLICT (project_id, idempotency_key) DO NOTHING` remains the concurrency boundary. No in-memory mutex is required in production.

## Authoritative durable identity

- Logical submission identity: authenticated principal + UUID4 submission key.
- Earliest durable aggregate: deterministic owner-scoped Project.
- Durable pre-planning registry: existing `research_submissions` record with a pre-reserved run ID.
- Product Research identity: WorkflowRun ID (`research_id == run_id`) once visible.

The key is opaque, not a credential, and does not authorize access. Existing UI authentication and Project/run authorization remain mandatory.

## Idempotency scope

One principal plus one UUID4 key denotes one logical action for the durable lifetime of the registry row. A fresh form action receives a fresh key and may intentionally submit an identical Brief. No Brief-level semantic deduplication or expiry/cleanup subsystem was added.

## Retry and reconciliation semantics

| Condition | Behavior |
|---|---|
| First submit | Creates/loads deterministic Project, wins atomic registry insert, then runs Planner once. |
| Replay while planning | Returns pending reconciliation; creates no Project/run and invokes no Planner. |
| Replay after run creation | Resolves the reserved run and redirects to its durable Research URL. |
| Replay after terminal | Resolves the same run/result. |
| Same key, changed Brief | HTTP 409 / idempotency conflict; no new work. |
| Malformed key | HTTP 422; no work. |
| Unknown reconciliation key | HTTP 404; no work. |
| New key, identical Brief | New intentional Research is allowed. |

Read path:

- `GET /ui/research/submissions/{submission_key}`
- `GET /ui/research/submissions/{submission_key}/status.json`

Both are read-only. Pending pages poll status and never POST or resubmit.

## Failure windows

1. **Project committed, registry absent:** no paid work has begun. Replay derives the same Project and may atomically register/take over.
2. **Registry committed, planning not started:** record is readable as pending; replay never plans.
3. **Planning active, client disconnects:** original server path continues; replay remains pending and does not duplicate Planner.
4. **Planner fails:** record is marked failed and retained. Replay fails closed to the same logical submission.
5. **Run creation/enqueue fails:** same failed-state behavior; deterministic Project and reserved run identity remain auditable.
6. **Run created, response fails:** reconciliation finds the reserved run and redirects to it.
7. **Server restart with pending record:** replay remains fail-closed; it does not silently rerun expensive work. Operational recovery of a genuinely abandoned pending record is an explicit remaining concern, not automatic duplicate execution.

## UI behavior

- Hidden UUID4 key is issued with each new form page.
- Same DOM action/repost retains the same key.
- Refreshing the blank new-form page creates a new action/key.
- Button disabling remains a UX guard only.
- Pending page states that refresh is safe and resubmission is not.
- JavaScript retries only the read endpoint, never POST.
- No API key, Bearer token, or internal credential is exposed.

## Safe future P1-26.2 procedure

1. Load `/ui/research/new` once and record its submission key before clicking.
2. Submit exactly once; that action consumes the paid-run authorization.
3. Normal 303: follow the returned Research deep link.
4. Timeout/stale navigation: do not POST again.
5. Open `/ui/research/submissions/{recorded-key}` or its status JSON.
6. Reconcile pending state until the reserved run becomes visible, then follow `research_url`.
7. Unknown key/absence is not permission to retry; stop and request explicit authorization.

## Remaining risks

- A process crash leaving a pending record before run creation is fail-closed and requires an explicit future recovery policy; it cannot duplicate paid work automatically.
- PostgreSQL concurrent `ON CONFLICT` behavior is relied upon in production; existing PostgreSQL integration tests remain environment-gated.
- Registry rows currently have no expiry. This is acceptable because a new UUID key creates a distinct intentional action; retention policy remains a separate operational concern.
