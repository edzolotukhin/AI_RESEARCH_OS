## A. Scope

P1-07.6B introduces a stable, provider-neutral **response classification** for each Evidence inner-chunk LLM response.

It uses:

1. normalized `LLMResponse` completion metadata (P1-07.6A);
2. visible content facts (`len(content)`);
3. existing strict `JsonExtractor` / `JsonValidator` + Evidence payload contract.

This phase does **not** retry, salvage, repair JSON, change budgets, prompts, models, grounding, or provenance.

---

## B. Taxonomy

`EvidenceResponseClassification` (`application/evidence/evidence_response_classification.py`):

| Value | Meaning | Failure? |
|-------|---------|----------|
| `incomplete_provider_output` | Provider completion incomplete/truncated | Yes |
| `empty_provider_output` | Completed (or unknown) with zero-length visible content | Yes |
| `invalid_json` | Non-empty content, no valid JSON value | Yes |
| `root_type_mismatch` | Valid JSON whose root is not an object | Yes |
| `schema_contract_mismatch` | Root object fails Evidence `items` contract | Yes — typed fail-closed (P1-07.6B.1) |
| `valid_empty_result` | Root object with `items=[]` | **No** |
| `valid_candidates` | Root object with `items` list length ≥ 1 | **No** |

Persisted field: `response_shape.response_classification`.

This is **not** `failure_classification`. The latter remains the stage-level diagnostic (`no_candidates`, `grounding_rejected_all`, …).

---

## C. Precedence

Deterministic order:

1. **Provider completion first.**  
   `was_truncated` **or** `incomplete_reason is not None` → `INCOMPLETE_PROVIDER_OUTPUT`  
   regardless of empty / partial / apparently valid JSON. **No salvage.**

2. **Empty visible output.**  
   `len(content) == 0` → `EMPTY_PROVIDER_OUTPUT`

3. **Strict JSON parse.**  
   No valid JSON value → `INVALID_JSON`

4. **Root validation.**  
   Valid JSON, root not object → `ROOT_TYPE_MISMATCH`

5. **Evidence schema contract.**  
   Root object missing `items`, `items` null, or `items` not a list → `SCHEMA_CONTRACT_MISMATCH`

6. **`items=[]`** → `VALID_EMPTY_RESULT`

7. **`items` list length ≥ 1** → `VALID_CANDIDATES`  
   Item-level filtering / grounding / provenance do **not** change this class.

### Whitespace-only decision

`content == "   \\n\\t"` has `len > 0`. Existing `JsonExtractor.extract_all` returns no containers for whitespace-only / non-container text that fails `json.loads`. Classification: **`INVALID_JSON`**, consistent with historical `_parse_payload` raising `ValueError`.

Empty string (`len == 0`) remains **`EMPTY_PROVIDER_OUTPUT`**, distinct from whitespace.

## E. Typed representation

- Enum: `EvidenceResponseClassification(str, Enum)` — serializable `.value` strings.
- Fail-closed exception: `EvidenceResponseOutcomeError(ValueError)` with `.classification`.
- Classification is computed from explicit state, **never** by parsing exception messages.

## F. Parser / schema boundary

**Parser (unchanged acceptance):** first valid JSON object via `JsonExtractor` + `JsonValidator`. Non-container roots (`null`, `"foo"`, `123`, `true`) are detected with the same `JsonValidator` fallback already used by P1-07.4.1 shape diagnostics. No repair / salvage.

**Evidence schema contract (actual current contract):**

Top-level object **must** contain `items` as a **list**.

| Payload | Classification | Extractor yield |
|---------|----------------|-----------------|
| missing `items` (`{"evidence":[]}`) | `SCHEMA_CONTRACT_MISMATCH` | `EvidenceResponseOutcomeError` (P1-07.6B.1) |
| `items` wrong type (`{"items":"x"}`) | `SCHEMA_CONTRACT_MISMATCH` | `EvidenceResponseOutcomeError` (P1-07.6B.1) |
| `items: null` | `SCHEMA_CONTRACT_MISMATCH` | `EvidenceResponseOutcomeError` (P1-07.6B.1; no longer `TypeError`) |
| `items: []` | `VALID_EMPTY_RESULT` | `[]` success |
| `items: [{...}, ...]` | `VALID_CANDIDATES` | existing item filter → candidates |

Item-level defects (missing need id, empty statement, non-object item, unknown need) remain **filter rejections** under `VALID_CANDIDATES` / empty post-filter — not schema mismatch and not grounding.

Grounding / provenance run **after** this classification and must not rewrite it.

## G. Exception behavior

| Classification | Exception |
|----------------|-----------|
| `EMPTY_PROVIDER_OUTPUT` | `EvidenceResponseOutcomeError` |
| `INCOMPLETE_PROVIDER_OUTPUT` | `EvidenceResponseOutcomeError` |
| `INVALID_JSON` | `EvidenceResponseOutcomeError` (message still `LLM evidence payload must be a JSON object`) |
| `ROOT_TYPE_MISMATCH` | `EvidenceResponseOutcomeError` (same message; type via `.classification`) |
| `SCHEMA_CONTRACT_MISMATCH` | `EvidenceResponseOutcomeError` (P1-07.6B.1 fail-closed) |
| `VALID_EMPTY_RESULT` | none |
| `VALID_CANDIDATES` | none (unless existing item construction errors) |

`EvidenceResponseOutcomeError` subclasses `ValueError` so existing `assertRaises(ValueError)` contracts remain valid.

---

## H. VALID_EMPTY_RESULT semantics

Completed `{"items":[]}`:

- classification = `valid_empty_result`
- extractor returns `[]`
- inner status = success / `inner_calls_zero_candidates`
- **not** a provider failure
- **not** `EMPTY_PROVIDER_OUTPUT`

---

## I. VALID_CANDIDATES semantics

Completed object with `items` list length ≥ 1:

- classification = `valid_candidates` even if all items are later filtered or grounding-rejected
- downstream grounding / provenance unchanged
