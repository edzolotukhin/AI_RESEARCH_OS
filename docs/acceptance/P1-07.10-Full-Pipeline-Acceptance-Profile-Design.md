# P1-07.10 — Full-Pipeline Acceptance Profile Design

**Status:** DESIGN / OFFLINE — no overlay implemented
**Branch:** `acceptance/live-desk-research-01`
**Date:** 2026-08-09
**Reference live run:** `a0eade60-f036-41f2-ac10-857e87fcdc29` (P1-07.9 PASS)
**SHA context:** Evidence reasoning hardening already on HEAD; readiness/search/evidence semantics unchanged

This note designs the smallest controlled resource envelope under which the existing Serbia Microgreens 12-InformationNeed brief has a realistic chance to become `ready_for_analysis` and therefore execute Analysis → Report → Review **without weakening product quality gates**.

It does **not** implement a compose overlay. `docker-compose.lowcost.yml` remains the diagnostic/cost-bounded profile.

---

## 1. Executive verdict

P1-07.10 **PASS** as a design/offline contract.

The live not-ready outcome was product-correct (P1-07.9). The low-cost overlay is structurally too small for a 12-need all-IN readiness rule. A **separate** full-pipeline acceptance overlay can give the current semantics a realistic opportunity if it expands:

1. source **attempt** breadth (primary bottleneck)
2. Evidence call capacity for initial chunks **plus** targeted extraction (same stage budget)
3. Sufficiency capacity using the real formula `evidenced_needs × (1 + targeted_reevals)`
4. Analysis/Report caps to match **per-RQ batching** (low-cost 2/2 is insufficient for a ready 6-RQ run)
5. Global `LLM_MAX_CALLS_PER_RUN` so stage caps, not the global cap, remain the control mechanism

**Recommended candidate:** Profile B — Balanced Full-Pipeline Acceptance.

**Architectural risk (not a silent GO to “just raise caps forever”):** Search allocation is **not** need-fair. Raising `SOURCE_MAX_SOURCES_PER_RUN` alone does not guarantee 12-need exposure. If a Profile B live run still covers only a handful of needs, the prerequisite is a Search fairness/scheduler change — not another doubling of budgets.

**GO** for P1-07.10.1 implementation of a **separate** overlay file. **NO-GO** for mutating `docker-compose.lowcost.yml` or production defaults.

Live `a0eade60` under `docker-compose.lowcost.yml`:

|-------|-------------|-------------|
| Search queries | 12 (one per IN) | all executed |
| Unique URL groups | 36 | pool after per-need slice=3 |
| `SOURCE_MAX_SOURCES_PER_RUN` | 5 | **5 URL attempts** (not 5 successes) |
| Successful / failed | — | 3 / 2 |
| Skipped | — | 31 budget-skipped |
| Need coverage | target 1.0 | **3 / 12**, target unsatisfied, Search still completed |
| Evidence queue | 23 work items | only IN4 / IN7 / IN9 represented |


Low-cost remains valuable as a **diagnostic envelope**. It must not be redefined into a full-pipeline profile.

## 3. Search / source capacity

### Exact scheduling

`SearchQueryBuilder` emits **one query per InformationNeed**, in design order. `priority` is not used.

`_collect_candidates`:

- provider search per query (`max_results` = `SOURCE_MAX_CANDIDATES_PER_QUERY`)
- keep `candidates[:SOURCE_MAX_CANDIDATES_PER_INFORMATION_NEED]`
- group by canonical URL

`_prioritize_groups` sort key:

1. `-need_coverage` (how many distinct INs share that URL)
2. `best_rank` (best provider rank)
3. `canonical_url`

**Not** need-first round-robin. **Not** priority-weighted.

`_acquire_candidates` enforces `SOURCE_MAX_SOURCES_PER_RUN` as:

```
if index >= source_group_limit: skipped_budget += 1; continue
```

So the cap is on **unique URL groups processed**, not successful sources. Failed retrievals consume a slot (`did_fetch` increments `attempted`; failures still advance `index`). Project duplicates increment `skipped_duplicate` without fetch but still consume an index slot.

Why 12 queries → 5 URL attempts: 36 unique groups, cap 5, remainder 31 skipped. Matches live.

### Minimum source cap to expose 12 needs

Do **not** assume 12 successful sources.

- Lower bound to *attempt* one distinct URL per need if the ranked list were 1:1 with needs: **12**
- Live success signal 3/5 is scenario-only, not a future rate
- Because sort is rank/overlap, 12 attempts can still cluster on high-rank needs
- Recommended controlled attempt envelope: **18** (half of the live 36-URL pool; ~1.5× needs)
- High-confidence: **24** (two-thirds of that pool)

`SOURCE_MAX_CANDIDATES_PER_INFORMATION_NEED=3` matters for **pool size**, not attempt fairness. Keep 3 for A/B (enough diversity into a 18–24 attempt window). Profile C may raise query/need slices to product default 5.

`SOURCE_MIN_SUCCESSFUL_SOURCES=3` is an early-stop conjunct, not a coverage guarantee. Keep 3.

### Fairness (section 7)

| Question | Answer |
|----------|--------|
| A. Fair across needs? | **No.** Rank + overlap sort. |
| B. Higher cap still consumed by early/high-yield needs? | **Yes, possible.** |
| C. `SOURCE_MAX_CANDIDATES_PER_INFORMATION_NEED` relevant? | Yes for pool membership; not a scheduler fairness knob. |
| D. Need-first round-robin? | **No** at Search. Evidence queue **is** need-fair among *represented* needs only. |
| E. Fairness setting vs larger cap? | Current code has **no** fairness env var. Profile-only lever is a larger attempt cap. |

**Risk classification:** Search fairness cannot be guaranteed by profile configuration. This is the main reason Profile B is “realistic chance,” not “deterministic 12-need coverage.”

## 4. Evidence capacity

Queue: `build_need_fair_extraction_queue` — one work item per outer chunk; bucket by **primary** need id; round-robin first chunks across represented needs, then second chunks.

Service passes `work_item.chunk.text` into the extractor. `ChunkedEvidenceExtractor` typically yields **one inner generate() per outer work item** (8000-char outer chunks). Live 8 calls = 8 work items.

One call may emit candidates for every need listed on that source’s run-scoped context, not only the primary bucket need. Repeated calls are additional chunks of the same source/need, not a second global pass.

Cap=8 is structurally too small **once 12 needs are represented**: the first 12 fair-queue slots are first chunks of 12 needs; cap 8 would starve 4 needs even with perfect Search.

Live 23 items / 3 long sources ≈ 7–8 chunks/source is a long-document signal, not a universal rate. Mixed web pages are often 1–3 chunks.

| Bound | Value | Rationale |
|-------|-------|-----------|
| Lower | 12 | first chunk × 12 represented needs |
| Recommended (B) | 36 | 12 first + 12 second-chunk depth + 12 targeted first-chunks |
| Upper safety (C) | 48 | more depth + 2 targeted sources/gap without turning into product-default 50 |

Do not blindly use 12: multi-chunk sources and targeted extraction share the same counter.

## 5. Sufficiency capacity

`HybridResearchSufficiencyEvaluator.evaluate`:

- `evidence_count == 0` → `MISSING`, **no LLM**
- else → exactly one `semantic.assess` per evidenced need

`ResearchLoopService` calls `evaluate` **again after every targeted iteration**, and each pass re-assesses **all currently evidenced needs**, not only the targeted IN.

Formula (actual code):

```
S_calls ≈ E × (1 + G)
```

- `E` = number of needs with ≥1 persisted evidence at that evaluation
- `G` = number of completed targeted iterations that trigger a re-eval
- initial readiness pass is the `1`
- optional second re-eval after another targeted attempt is included in `G`

Worst case if all 12 needs are evidenced from the start and one round services all 12 gaps once: `12 × 13 = 156`. That is not a sane acceptance envelope. Targeted research must remain a **residual** closer, not the primary coverage mechanism.

Intended controlled `G`:

| Profile | Intended G | `12 × (1+G)` | Proposed cap |
|---------|------------|--------------|--------------|
| A | 1 | 24 | 24 |
| B | 2 | 36 | 36 |
| C | 3 | 48 | 48 |

If initial Search+Evidence fails to evidence most needs, sufficiency spend stays small (zero-evidence = free) but readiness cannot become true. The profile bets on initial breadth.

## 6. Global LLM budget

Stage caps (with a stage key in `_STAGE_LLM_CALL_LIMITS`) are enforced in `assert_can_call`. Planner/search have **no** stage cap; planner counts toward the global total. Search uses no LLM.

Downstream reserve during Evidence:

```
reserve = sufficiency + analysis + report + review
allowed_before_downstream = LLM_MAX_CALLS_PER_RUN - reserve
```

Therefore a full successful run requires:

```
LLM_MAX_CALLS_PER_RUN
  ≥ planner_worst + Evidence + Sufficiency + Analysis + Report + Review
```

Planner worst case used here: `3` semantic attempts × `3` structured-output attempts = **9** (no stage cap; conservative).

| Profile | Planner | E | S | A | R | V | Envelope | Proposed global |
|---------|---------|---|---|---|---|---|----------|-----------------|
| Low-cost | ≤9 | 8 | 6 | 2 | 2 | 1 | 28 | **24 — already tighter than envelope** |
| A | 9 | 20 | 24 | 8 | 10 | 1 | 72 | 80 |
| B | 9 | 36 | 36 | 10 | 12 | 3 | 106 | **120** |
| C | 9 | 48 | 48 | 14 | 20 | 7 | 146 | 160 |

Low-cost global 24 vs downstream reserve `6+2+2+1=11` leaves only 13 calls for planner+evidence before reserve trip — consistent with Evidence stopping at 8 and never reaching A/R/R.

Recommendation: set global **above** the controlled envelope so **stage caps** remain the intended brakes.

## 7. Targeted research / gap rounds

Gap order: `(research_question_id, information_need_id)` → IN1 first (live).

**One round can service many gaps.** `while True` picks the next eligible gap until none remain, ready, or sufficiency budget ends. `RESEARCH_MAX_GAP_ROUNDS_PER_RUN=1` is not “one InformationNeed.” Live serviced only IN1 because sufficiency exhausted after one re-eval.

`TARGETED_MAX_ATTEMPTS_PER_GAP=1` is brittle **for the same gap** (cannot retry IN1 after a useless source) but does not block other gaps.

Targeted Evidence: `ProductionTargetedResearchRunner.run` → `extract_for_source_ids` → same `EVIDENCE_MAX_LLM_CALLS` / same `assert_can_call("evidence")`. Live: cap already 8/8 → 0 generate → 0 new evidence despite an acquired IN1 source.

Minimal targeted settings:

| Knob | A | B | C |
|------|---|---|---|
| `RESEARCH_MAX_GAP_ROUNDS_PER_RUN` | 1 | **2** | 2 |
| `TARGETED_MAX_ATTEMPTS_PER_GAP` | 1 | **2** | 2 |
| `TARGETED_MAX_QUERIES_PER_GAP` | 1 | 1 | 2 |
| `TARGETED_MAX_SOURCES_PER_GAP` | 1 | 1 | 2 |

B keeps query/source=1 (cost) but allows a second attempt on a stubborn gap and a second round if round 1 improved something.

One round is **not** sufficient as the sole recovery path for a 12-need brief when initial Search covers 3 needs. It is sufficient as a residual closer **if** initial coverage is broad.

## 8. Targeted Evidence budget interaction

Proven: targeted extraction shares `EVIDENCE_MAX_LLM_CALLS`.

Consequence: if the initial Evidence stage exhausts the cap, targeted research can acquire sources that never enter extraction. Sufficiency then re-judges the same evidence. Loop looks “active” in history (`new_sources_count>0`, `new_evidence_count=0`).

Profile-only options:

| Rank | Option | Verdict |
|------|--------|---------|
| **1** | **A. Increase Evidence cap for initial + targeted** | Only implementable-by-profile fix. Chosen for A/B/C. |
| 2 | B. Reserve Evidence budget for gap rounds | Better control; **architecture**. |
| 3 | C. Separate targeted Evidence budget | Cleanest accounting; **architecture**. |

Do not implement B/C in P1-07.10.1 unless Profile B live still shows targeted sources with zero extract after a raised cap (then B/C become prerequisites).

## 10. Source coverage target semantics

`SOURCE_MIN_INFORMATION_NEED_COVERAGE_RATIO=1.0` means:

- `_coverage_target_satisfied` ↔ every design InformationNeed appears on at least one **successful** source
- together with `acquired >= min_successful_sources`, this **may early-stop** further URL attempts (`coverage_complete_early_stop`)
- it is **not** a hard gate: Search still completes; `coverage_target_satisfied=false` is recorded; limitations list missing INs
- it does **not** feed readiness aggregation
- it is operator diagnostic + early-stop target, not a readiness input

Live completed because the run cap hit 5 attempts before the 1.0 target could be met. Early-stop never fired.

**Keep 1.0 on all acceptance profiles.** Lowering it would weaken a coverage aspiration and would not change readiness semantics; it would only make Search stop earlier — the opposite of what this brief needs.

## 11. Analysis / Report / Review budgets

Low-cost `ANALYSIS=2`, `REPORT=2`, `REVIEW=1` were never exercised on `a0eade60` (gate skip). Code tracing shows they are **not** sufficient for one normal **successful** 6-RQ acceptance run.

### Analysis

`batch_evidence_by_question` → one `analyze_findings` per RQ batch (and extra batches if >20 items or >12k chars). Then **one** `analyze_insights` over all findings.

Happy path: **6 + 1 = 7**. Cap 2 would stop mid-findings or block insights (`BudgetExhaustedError` → `AnalysisError`). No structured-output retry wrapper on analysis (single generate per batch).

Must raise. A=8, B=10, C=14 (product default).

### Report

`batch_findings_by_question` → one `generate_sections` per RQ batch. Then RQ-correction loop (`report_max_rq_correction_attempts` default 2, per missing RQ). Then `generate_summary`.

Structured-output retries: up to 3 generate() per engine call; each counts.

Happy first-attempt path: **6 sections + 1 summary = 7**. Cap 2 cannot complete a 6-RQ report. A=10, B=12, C=20.

### Review

`build_rq_batch_inputs(..., max_batches=REVIEW_MAX_CALLS)`. `REVIEW_MAX_CALLS=1` → a single semantic batch. Technical completion is possible on first-attempt parse.

Brittleness: structured retries also count; cap 1 ⇒ **zero retry budget**. One parse miss → review stage cap / failure.

A keeps 1 (minimal). B raises to **3** (retry-safe one/few batches). C uses product default **7**.

`review_max_revision_attempts=1` is unchanged (not a compose knob in low-cost). One REVISE cycle may call report again — Profile B report cap 12 includes modest slack; still not sized for a full second report rewrite. Acceptance policy should treat first-pass APPROVE as the expected path; REVISE is residual.

## 12. Full-pipeline acceptance criteria

Workflow `completed` is **not** enough. Insufficient research is a controlled terminal `completed` with A/R/R skipped (P1-07.9).

### Technical success

All of:

- Collect sources = `completed` (not failed)
- Extract evidence = `completed`
- Assess research readiness = `completed`
- Analyze findings = `completed` (**not skipped**)
- Write research report = `completed` (**not skipped**)
- Review research report = `completed` (**not skipped**)
- Workflow terminal without task-level technical failure (`BudgetExhaustedError` uncaught, extractor crash, report zero-sections, review reject-as-error)

### Research-quality success

All of:

- `ready_for_analysis = true`
- `research_outcome` consistent with ready (not `insufficient_research`)
- **every** required InformationNeed is `SUFFICIENT` under **current** readiness policy (all-IN, not a lowered bar)
- final report artifact exists
- review completes under **existing** acceptance policy (typically `APPROVE`; do not weaken review to force green)

Do **not** accept “reached Report because we skipped readiness.” Do **not** lower `SOURCE_MIN_INFORMATION_NEED_COVERAGE_RATIO` or all-IN aggregation to force the chain.

## 17. Recommended profile and rationale

**Select Profile B.**

| Criterion | Why B |
|-----------|--------|
| Cost | ×5 global vs low-cost, not C’s ×6.7; targeted queries stay 1 |
| Breadth | 18 attempts vs live 36-URL pool is the smallest attempt window with a plausible shot at most needs |
| Determinism | Stage math is deterministic; Search rank order is not — B documents that risk instead of buying C’s extra slice size as a false guarantee |
| Safety | Global 120 > envelope 106; stage caps remain brakes; coverage ratio and all-IN readiness untouched |
| Acceptance probability | Removes every **structural** impossibility (source<12, evidence<12, sufficiency=6, A/R=2) and leaves headroom for 2 targeted re-evals + multi-chunk extract |
| Diagnostic value | If B still fails ready, the failure distinguishes fairness/legacy-semantics vs “caps too small” better than C |

Not A: 12 source attempts + evidence 20 + G=1 is still likely to reproduce clustered coverage and targeted-extract starvation on long sources.

Not C: higher cost without fixing Search fairness; better as a fallback after B fails for budget reasons rather than fairness.

## 22. Architecture vs profile-only limit

Profile configuration **can** remove the structural impossibilities that made `a0eade60` unable to become ready.

Profile configuration **cannot** guarantee need-fair source allocation.

Decision rule application:

- Proceed with Profile B overlay implementation (P1-07.10.1)
- If live B still shows ≪12 needs represented after 18 attempts, **stop raising caps** and schedule a Search fairness design (need-round-robin or priority-aware attempt allocation) as the prerequisite
