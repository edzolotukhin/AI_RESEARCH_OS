# P1-26.1 — Bounded Complementary Retrieval Portfolio

## A–B. Executive verdict / PROPERTY AC

**PROPERTY AC: PASS offline.** Initial Search now derives an ordered provider-neutral portfolio containing mandatory `BASELINE` and, only when the provider confirms safe support for a resolvable single-country geography, one complementary `LOCALIZED` arm. Both arms preserve the same complete `SearchQuery`, PROPERTY AA projection, category, geography, IN intent, timeframe, language, source preferences, and `max_results=5`. Tavily translates only the localized arm into `country=<resolved country>`.

Candidates from both arms are unioned and canonicalized before PROPERTY Y ranking and the existing source-attempt cap. A duplicate URL is fetched at most once while discovery records preserve both arm observations. No arm preference enters ranking or P1-12 authority semantics.

P1-26.1 is deliberately **initial-search-only**. Targeted/remediation builders explicitly produce baseline queries and retain existing directive/query/source/Evidence bounds; they are not multiplied by portfolio arms.

## C–D. Old and new retrieval topology

Old initial topology:

`InformationNeed → one SearchQuery → one Tavily request (country applied by the P1-25.1 direct-adapter behavior) → normalization → URL grouping → PROPERTY Y/P1-12 ranking → source cap → acquisition → lineage`

New initial topology:

`InformationNeed → one semantic SearchQuery → derive portfolio [BASELINE, LOCALIZED?] → one or two provider requests → candidate union → canonical URL grouping → PROPERTY Y/P1-12 ranking → unchanged source cap → one acquisition per canonical group → multi-arm discovery lineage`

For one eligible IN: maximum two calls. For 12 eligible INs: old maximum 12, new explicit maximum 24. Non-eligible or unsupported-provider INs remain one baseline call. No hidden retry was added.

## E–F. Retrieval-arm abstraction and provider neutrality

`domain/sources/retrieval_arm.py` defines only semantic strategies:

- `RetrievalArm.BASELINE`
- `RetrievalArm.LOCALIZED`

It contains no Tavily, country-enum, Ukraine, pizza, domain, language, or provider vocabulary. `SearchQuery.retrieval_arm` is transient and excluded from serialization. `SearchProvider.supports_retrieval_arm()` is a provider capability query with a default that supports baseline only. The application derives arms; infrastructure translates a supported localized arm into its own provider option.

## G–H. BASELINE and LOCALIZED semantics

BASELINE reproduces P1-24.1's provider request:

```text
{api_key, query: provider_query_text or query_text, max_results: 5}
```

LOCALIZED uses the same `SearchQuery` values and adds only:

```text
country: <resolved supported country>
```

Search depth/topic remain omitted/default basic/general. There is no rewrite, translation, date/domain filter, second provider, higher result limit, or speculative strategy.

## I–K. Derivation and boundedness

`derive_initial_retrieval_portfolio()` always creates baseline first and asks the configured provider whether localized is safe. Its hard maximum is `MAX_INITIAL_RETRIEVAL_ARMS_PER_INFORMATION_NEED = 2`.

| Geography/provider condition | Portfolio |
|---|---|
| Supported explicit single country | baseline + localized |
| City + explicit supported country | baseline + localized |
| Global/worldwide | baseline only |
| Region such as Europe | baseline only |
| Multiple countries | baseline only |
| Unknown/missing/unsupported geography | baseline only |
| Provider without localized capability | baseline only |

No future arm type can multiply independently because the derivation function currently knows exactly these two arms and applies the hard slice.

## L–N. Initial integration and targeted/remediation decision

Initial integration occurs in `SourceAcquisitionService.acquire_for_context()` after `SearchQueryBuilder` creates one semantic query per IN and before `_collect_candidates()` makes provider calls. Summary diagnostics report the actual provider-call count and per-arm counts.

Targeted/remediation is **not integrated** in P1-26.1. `TargetedSearchQueryBuilder` explicitly marks every base/directive query as baseline. `acquire_targeted_queries()` does not invoke portfolio derivation, so its exact bound remains:

`≤ max_queries_per_gap provider calls; ≤ max_sources_per_gap acquisitions; existing per-attempt Evidence limit`

This avoids `missing aspects × directives × arms × retries` multiplication and preserves P1-07 bounded remediation. A localized targeted arm requires a later property with a separate arm/call budget.

## O–P. Lineage and persistence/schema impact

Each normalized candidate carries bounded metadata including provider, retrieval arm, country application/status, depth label, result limit, and provider score. Durable `discovery_records` now add:

- `retrieval_arm`
- `provider_country` when localized

Existing IN, RQ, query, run, design, provider, and rank fields remain. Discovery identity includes retrieval arm, so `IN2/baseline/rank2` and `IN2/localized/rank1` remain distinct even for one canonical URL.

No table, migration, repository, cache, dependency, or durable domain column was added. The existing Source metadata JSON contract carries bounded arm lineage. Older records without the field default to `baseline` in merge keys.

## Q–R. Cross-arm dedup and source-attempt protection

`_collect_candidates()` canonicalizes and groups results from all arms before `_select_groups()` and `_acquire_candidates()`. Therefore:

- baseline A + localized A → one canonical group;
- baseline A/B + localized B/C → A/B/C;
- ranks remain inspectable as separate discovery records;
- the group uses the existing deterministic best-rank/relevance behavior;
- a cross-arm duplicate cannot consume a second fetch or source-attempt slot solely because it appeared twice.

## S–T. PROPERTY Y and P1-12

Retrieval-arm information is absent from `deterministic_source_relevance.py` and `selection_sort_key`. After union/dedup, the accepted ordering remains category tier, P1-12/expectation and authority semantics, topical/need/geography relevance, provider rank, and canonical URL. LOCALIZED is not globally promoted over BASELINE. Country discovery is not credibility.

## U–W. PROPERTY AA, PROPERTY AB, and Tavily

PROPERTY AA projection is byte-equivalent across both arms. `SearchQuery.to_dict()/from_dict()` remains unchanged and does not persist `provider_query_text` or arm.

PROPERTY AB's deterministic country resolver and Tavily-supported country capability set are reused. Direct legacy adapter calls with no explicit arm retain P1-25.1 localized behavior for backward compatibility; production initial portfolio execution always sets baseline/localized explicitly.

Tavily behavior:

- baseline: no country;
- localized + safely resolved supported country: country added;
- all other request parameters unchanged;
- capability resolution performs no provider call.

## X. Auditability metadata

Provider calls/results are attributable through:

- IN and SearchQuery IDs;
- `retrieval_arm` on the transient query/candidate;
- unchanged projected query at the call boundary;
- normalized provider name, arm, resolution status, applied boolean, safe country, effective basic depth label, max results, score;
- summary `retrieval_arm_call_counts` and actual `queries_executed`;
- durable bounded Source discovery records.

No API key, Authorization header, raw request envelope, or raw provider response is persisted.

## Y–Z. Fail-open and localized failure semantics

If portfolio derivation cannot safely create localized, baseline executes exactly once. If the provider reports no capability, baseline-only is used. If a localized call raises `SearchProviderError`, the already completed baseline results remain in the candidate union, a bounded non-secret warning is emitted, and processing continues. Baseline provider failure retains the existing fail-fast behavior. There is no retry or replacement call.

## BB–BH. Boundary, risks, and next step

PROPERTY AC does **not** solve provider/index recall. It preserves and combines two empirically complementary Tavily representations so downstream selection can see their union. If both arms miss a source, the portfolio cannot invent it.

PROPERTY AC **does establish the minimum retrieval-diversification architecture**: explicit semantic arms, provider capability translation, bounded call topology, union/dedup, multi-arm lineage, baseline preservation, and failure isolation.

Remaining risks:

1. Eligible initial Search can double provider Search credits/calls from 12 to 24; source/Evidence budgets remain unchanged.
2. Localized failure observability is logged and summarized indirectly; a zero-result call has no candidate-level durable record.
3. Arm lineage uses existing JSON metadata rather than a query-attempt entity.
4. Targeted/remediation localized diversification is intentionally deferred.
5. Only one provider and two empirically justified representations exist; provider-index monoculture remains.

Another provider-only experiment before commit: **NO**; P1-25.2 already established complementarity and this task is offline architecture acceptance. A paid/full Research run before commit: **NO**.

Commit recommendation: **READY_TO_COMMIT**. Next: run a separate final commit gate, push separately, refresh runtime, then run one deliberately authorized live acceptance to verify arm counts, lineage, dedup, budget behavior, and Source/Evidence topology—not another speculative provider-only tuning experiment.
