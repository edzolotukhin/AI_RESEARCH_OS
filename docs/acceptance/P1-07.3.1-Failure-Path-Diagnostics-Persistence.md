# P1-07.3.1 — Failure-Path Diagnostics Persistence

## Status

**P1-07.3.1 FAILURE-PATH DIAGNOSTICS PERSISTENCE — PASS**

Observability-only milestone. No extraction, grounding, budget, or workflow outcome semantics changed.

---

## A. Prior limitation

P1-07.3 added structured evidence diagnostics (`EvidenceExtractionSummary.diagnostics`) but:

1. `EvidenceExecutor.run()` called `extract_for_context()` then wrote shared state — **never reached on `EvidenceExtractionError`**.
2. `WorkflowRuntimePersister.on_task_finished()` captured task snapshots **only for `COMPLETED`** tasks.
3. Failed evidence runs therefore lost forensic payload in durable `task_results` and `GET /workflow-runs/{run_id}/results`.

---

## B. Exact failure path (before)

```
EvidenceExecutor.run()
  → extract_for_context()
  → _extract_work_queue()
  → extracted == 0
  → raise EvidenceExtractionError          [diagnostics built but discarded]
  → TaskExecutor.execute() catches
  → task.status = FAILED
  → WorkflowRuntimePersister.on_task_finished()
      → skips capture_task_result (not COMPLETED)
  → workflow FAILED
  → GET /results: no evidence_extraction diagnostics
```

---

## C. Persistence boundary chosen

Two narrow boundaries (existing infrastructure):

| Layer | Responsibility |
|-------|----------------|
| `EvidenceExtractionService` | Attach completed `EvidenceExtractionSummary` (with diagnostics) to `EvidenceExtractionError.summary` before raise |
| `EvidenceExecutor` | On catch: persist summary to `shared_state` + `intermediate_results` via `try_persist_evidence_failure_diagnostics()`, then re-raise |
| `WorkflowRuntimePersister.on_task_finished()` | Capture failed task snapshot when `has_evidence_failure_diagnostics(context)` |

Helper module: `application/evidence/evidence_failure_diagnostics_persistence.py`

---

## D. Why this boundary is canonical

- **Task result snapshots** (`capture_task_result`) are the existing durable channel for stage outputs (`shared_state` merge).
- **EvidenceExecutor** is the narrowest stage boundary that owns workflow context on failure.
- **Persister** already checkpoints `task_results` to PostgreSQL — extending failed-task capture reuses the same path as success without a parallel storage system.
- Diagnostics are **not recomputed** — the same P1-07.3 object attached to the exception is persisted.

---

## E. API / results access path

After a failed evidence task:

```
GET /workflow-runs/{run_id}/results
  → task_results[].snapshot.shared_state.evidence_extraction
      → diagnostics.failure_classification
      → diagnostics.extractor_attempts
      → diagnostics.work_items[]
      → ... (full P1-07.3 schema)
```

Programmatic helper: `extract_evidence_extraction(task_results)` in `application/evidence/evidence_result_codec.py`

Example navigation:
```json
{
  "task_results": [
    {
      "task_id": "<evidence-task-id>",
      "snapshot": {
        "shared_state": {
          "evidence_extraction": {
            "evidence_extracted": 0,
            "diagnostics": {
              "failure_classification": "no_candidates",
              "extractor_attempts": 8,
              "work_items": [ ... ]
            }
          }
        }
      }
    }
  ]
}
```

No new public endpoint added.

## H. Failure-safety behavior

If diagnostic persistence raises:

- Original `EvidenceExtractionError` still propagates (task still fails).
- Persistence error recorded in `context.execution_metadata["evidence_diagnostics_persistence_errors"]`.
- Research failure is not converted to success.
