# P1-26.2D — Pending Submission Reconciliation

## Verdict

PROPERTY AD-P is implemented as a narrow pending-state reconciliation fix. No Research, provider, LLM, Search, Evidence, retrieval-portfolio, budget, persistence-schema, or dependency behavior is changed.

## Defect and corrected read boundary

The durable Project and `research_submissions` claim could exist while synchronous planning had not yet materialized the reserved WorkflowRun. The old facade immediately called `AuthorizationService.require_run()`. That service deliberately concealed a missing run as `AccessDeniedError`, so the UI route converted the valid pending submission to 404.

The corrected path is:

1. Normalize the opaque submission key.
2. Derive the principal-scoped canonical Project identity.
3. Authorize that Project for the authenticated principal.
4. Read the submission claim by `(project_id, idempotency_key)`.
5. Return a bounded pending projection when the reserved WorkflowRun genuinely does not exist.
6. Once a run exists, require exact Project linkage and normal run authorization before exposing workflow status.

Possession of a submission key is never sufficient authorization. Unknown keys, wrong owners, missing Projects, corrupt run linkage, and repository failures remain fail-closed.

## Pending projection

Pending HTML returns 200 and polls the existing JSON reconciliation path. Pending JSON preserves the durable submission status, Project ID, and reserved Research/run identity; it reports `SUBMITTING`, exposes no terminal outcome or task internals, and provides no Research deep link until the WorkflowRun exists.

The pending → materialized → terminal transition preserves the same reserved run identity. Reconciliation creates no Project, Planner call, WorkflowRun, provider call, or LLM call.

## Observability lesson

Absence of a completed Uvicorn access-log line does not prove that a synchronous POST is absent. The authoritative ambiguous-submit check is reconciliation using the retained submission key. A client must never infer retry permission from incomplete access logs, browser timeout, or transient pending state.

## Compatibility and boundaries

- Existing same-key, concurrent, and new-key submission behavior is unchanged.
- P1-19 API and P1-20 UI contracts remain unchanged.
- PROPERTY AC and all Search/Evidence behavior remain untouched.
- Existing `research_submissions` persistence is reused; no migration or dependency is added.
