## 2. Root causes

### 2.1 Sufficiency budget exhaustion → technical failure

`ResearchLoopService` and `ResearchReadinessService` did not translate stage-cap exhaustion into a controlled `INSUFFICIENT_RESEARCH` completion path. Valid readiness state existed but was lost when the exception propagated to `WorkflowEngine`.

Additionally, when gap-attempt bounds caused the loop to exit (`no_material_improvement`) while the sufficiency cap was already reached, budget termination was not detected.

### 2.2 Evidence extraction budget starvation

With `EVIDENCE_MAX_LLM_CALLS=8`, one large multi-chunk IN2 source consumed all extraction calls sequentially before IN1/IN3 eligible sources received an opportunity.

### 2.3 Observability inconsistency

`research_loop_state.research_loop_count = 4` while embedded `research_readiness.research_loop_count = 0` because final readiness persistence did not occur after mid-loop failure, and loop count was not merged from authoritative loop state on persist.

### 2.4 Not root causes (confirmed unchanged)

- Evidence attribution (`information_need_refs`) was correct.
- P1-06 semantic sufficiency behaved correctly and was not weakened.

---

## 3. Architectural decision

Distinguish **technical execution failure** from **controlled research termination due to configured budget exhaustion**.

When sufficiency budget is exhausted during bounded research:

| Outcome | Value |
|---------|-------|
| Workflow | `COMPLETED` |
| Research outcome | `INSUFFICIENT_RESEARCH` |
| `ready_for_analysis` | `false` |
| `targeted_research_required` | `false` |
| Termination reason | `sufficiency_budget_exhausted` |
| Downstream tasks | `SKIPPED` (existing gate semantics) |

Use existing domain vocabulary (`ResearchOutcome.INSUFFICIENT_RESEARCH`, `termination_reason`) rather than a parallel workflow state machine. Do **not** manufacture `SUFFICIENT` when budget ends.

Translation boundary: `ResearchReadinessService.assess_and_apply()` and `ResearchLoopService.run_bounded_loop()` — only for `BudgetExhaustedError` with reason `sufficiency_max_llm_calls`.

## 5. Why the fix is generic / platform-level

- Termination reason `sufficiency_budget_exhausted` is stage-scoped, not Serbia/microgreens-specific.
- Fair extraction uses sorted InformationNeed IDs and sorted source IDs — no domain ranking.
- Graceful handling is gated on explicit stage-cap reason matching, not broad `BudgetExhaustedError` swallowing.
- P1-06 semantic sufficiency rules, statuses (`MISSING` / `INSUFFICIENT` / `PARTIAL` / `BLOCKED` / `SUFFICIENT`), and policy logic are untouched.

## 6. Graceful budget termination semantics

### Before

```
sufficiency cap reached during loop re-eval
  → BudgetExhaustedError propagates
  → research_quality task FAILED
  → workflow FAILED
  → readiness not persisted / loop count stale
  → analysis/report/review SKIPPED (incidental)
```

### After

```
sufficiency cap reached (pre-check or on re-eval)
  → apply_sufficiency_budget_termination(previous_valid_result)
  → targeted_research_required = false
  → termination_reason = sufficiency_budget_exhausted
  → research_outcome = insufficient_research
  → research_quality task COMPLETED (no exception)
  → workflow COMPLETED
  → latest valid readiness + loop state persisted
  → analysis/report/review SKIPPED via ResearchReadinessGate
```

Unexpected exceptions and non-sufficiency `BudgetExhaustedError` (e.g. evidence stage, global run cap) still fail normally.

## 7. Evidence fairness algorithm

### Invariant

Before spending additional extraction calls on later chunks of an already-served need/source, give other uncovered InformationNeeds eligible sources an extraction opportunity where possible.

### Algorithm (`build_need_fair_extraction_queue`)

1. For each source (sorted by `source.id`), resolve run-scoped context and primary need = `sorted(information_need_ids)[0]`.
2. Split source content into chunks; append each chunk to that need's bucket (preserving chunk order within the source).
3. Round-robin dequeue: for each pass, take the next unprocessed chunk from each need bucket in sorted need-ID order until all buckets are empty.

### Properties

- Deterministic across repeated runs.
- Does not increase `EVIDENCE_MAX_LLM_CALLS`.
- Does not duplicate evidence or bypass `SourceAcquisitionBudget`.
- Provenance and `information_need_refs` unchanged (chunk extraction uses existing run-scoped context).
- Single-need multi-chunk behavior preserved (round-robin over one bucket = sequential chunks).

## 11. Budget semantics audit (Workstream 4)

### Expected domain termination (graceful)

| Layer | Condition | Handler |
|-------|-----------|---------|
| Evidence stage cap | `evidence_max_llm_calls` | `EvidenceExtractionService` / `ChunkedEvidenceExtractor` — partial evidence, stage continues |
| Evidence downstream reserve | `downstream_reserve_exhausted` at evidence stage | Same graceful evidence path |
| Sufficiency stage cap | `sufficiency_max_llm_calls` | **NEW:** `ResearchReadinessService` / `ResearchLoopService` → `INSUFFICIENT_RESEARCH` |
| Targeted research bounds | max rounds / no improvement | Existing controlled termination (`max_research_rounds`, `no_material_improvement`, etc.) |

### Must remain technical failure

| Layer | Condition |
|-------|-----------|
| Global run cap | `llm_max_calls_per_run` |
| Token caps | `max_input_tokens_per_run`, `max_output_tokens_per_run` |
| Wrong-stage exhaustion | e.g. evidence cap raised during sufficiency eval |
| Unexpected exceptions | Any non-budget error |
| Analysis / report / review stage caps | No graceful insufficient-research path (task failure) |

### Stages currently handling exhaustion gracefully

- Evidence (pre-existing)
- Sufficiency (P1-07.2)

### Stages that previously leaked `BudgetExhaustedError` to WorkflowEngine

- Sufficiency during targeted loop re-eval (**fixed**)
- Analysis, report, review — still fail task on cap (by design)

### Retry charging

Structured-output retries call `mark_llm_call_as_retry()` before retry; `BudgetEnforcingLLMClient.record_llm_call(..., retry=True)` increments both `llm_calls` and `retries` on the stage. Each retry consumes a full budget slot (correct for hard caps).

### Nested loop multiplication

Targeted research loop re-evaluations and structured-output retries are bounded by stage cap + global cap. No unbounded nested multiplication beyond configured limits.

### Post-cap provider calls

Pre-iteration `sufficiency_budget_available()` prevents scheduling another targeted iteration after cap is known exhausted. Evidence service checks `assert_can_call("evidence")` before each work item.

### Planner budget

Planner uses stage `"planner"` in `EXECUTOR_STAGE_MAP` but is **not** included in `_STAGE_LLM_CALL_LIMITS` — planner LLM calls are recorded against global `llm_max_calls_per_run` only, not a dedicated stage cap. `ensure_run_budget()` is invoked by `WorkflowEngine`, not by standalone planner flows.

**Assessment:** Acceptable for P1-07.2 gate. Planner-budget redesign is a separate future platform task unless a direct correctness dependency appears.

## 13. Remaining limitations

- Fair scheduling keys off primary need per source (`sorted(information_need_ids)[0]`). Sources tagged to multiple needs still attribute correctly but schedule under one bucket.
- Very tight caps may still yield thin cross-need coverage even with fairness (by design — fairness ≠ equal counts).
- Low-cost compose caps (`EVIDENCE=8`, `SUFFICIENCY=6`) remain unchanged; runs may complete as `INSUFFICIENT_RESEARCH` rather than analysis-ready.
- Planner LLM usage remains outside dedicated stage caps.
