---

## B. Exact old queue semantics

1. Eligible sources sorted by `source.id`
2. All chunks of each source appended into primary-need buckets
3. Need-fair round-robin across sorted need IDs
4. Within a need, source-id order meant long early sources consumed many RR slots with **depth** before later sources' first chunk

P1-16 consequence: DESNZ (IN9) first ordinal **44** > initial stop **38**.

---

## C. Final scheduling architecture

Two-phase deterministic queue in `build_need_fair_extraction_queue`:

**Phase 1 — first opportunity**
One first chunk per eligible unique Source, need-fair RR across primary INs.

**Phase 2 — depth**
Remaining chunks, same need-fair RR, source-id order within need.

Work unit unchanged: **Source × chunk**.

## E. First-opportunity definition

For each eligible Source (acquired path filtered by service; scheduler requires non-empty `content_text` + run-scoped need + ≥1 chunk): schedule **chunk_index=0** with `phase=first_opportunity` / `source_first_attempt=true` before any `phase=depth` item for any Source.

---

## F. Need-fair ordering

Phase 1 and Phase 2 both round-robin across `sorted(primary_need_id)`. Within a need bucket, sources ordered by `source.id`.

---

## G. Depth-phase behavior

After all first opportunities are queued, remaining chunks use the prior need-fair RR pattern (without re-introducing first chunks).

---

## H. Deduplication behavior

Before prepare: unique by `source.id`, then by `canonical_url` (lowest id wins). Multi-need Sources still get **one** Source-level first opportunity (primary = `sorted(need_ids)[0]`).

---

## I. Budget behavior

No new reserves. Same Evidence=50 / global=100 / downstream reserve math. Ordering consumes the existing envelope; if Sources > calls, a deterministic prefix is attempted and the rest are skipped.

---

## J. Zero-yield behavior

Unchanged billing: a first-opportunity call that yields empty/rejects still counts. No second phase-1 slot for that Source.
