## 2. Exact definition of `failure_classification`

Field: `EvidenceExtractionDiagnostics.failure_classification`

Defined in `application/evidence/evidence_extraction_diagnostics.py`.

Enum docstring (P1-07.3, commit `95d8a08`):

> Diagnostic-only taxonomy for a zero-evidence or partial evidence stage.

It is **not** a provider-response classifier.
It is **not** a task/workflow status.
It is **not** consumed by Research Readiness, Analysis, Report, Review, or the scheduler.

It is a post-hoc diagnostic label derived from:

1. whether any evidence was persisted (or counted as a dedup hit)
2. service-level extractor exceptions / `extractor_failures`
3. service-level candidate rejection counters (need-ref, provenance, grounding, empty/invalid)

It does **not** consume P1-07.6 `response_classification`.

## 3. Complete taxonomy

`EvidenceStageFailureClassification`:

| Value | Trigger (current `classify()`) | Provider failure required? | Persisted may be > 0? | Raw candidates may be > 0? | Stage can still complete? | Downstream meaning |
|-------|--------------------------------|----------------------------|------------------------|----------------------------|---------------------------|--------------------|
| `success` | `persisted_evidence > 0` and no service-level rejections/failures | No | Yes (required) | Yes | Yes | Observability only: clean persist path |
| `mixed_failure` | **Either** persisted > 0 with any rejection/failure **or** persisted == 0 with 2+ zero-yield categories | No | Yes or No | Yes or No | Yes, if persisted > 0 | Observability only |
| `no_candidates` | persisted == 0; extractor returned empty lists (or swallowed inner exceptions that yielded []) | No | No | No | No: `EvidenceExtractionError` unless `allow_empty` | Zero-yield diagnostic |
| `extractor_failure` | persisted == 0; `extractor_failures > 0` or `extractor_exceptions` (sole category) | Typical, not required | No | No | No (zero evidence) | Zero-yield diagnostic |
| `invalid_need_refs_all` | persisted == 0; only need-ref rejections | No | No | Yes | No | Zero-yield diagnostic |
| `provenance_rejected_all` | persisted == 0; only provenance rejections | No | No | Yes | No | Zero-yield diagnostic |
| `grounding_rejected_all` | persisted == 0; only grounding rejections | No | No | Yes | No | Zero-yield diagnostic |
| `budget_exhausted_before_evidence` | persisted == 0; stop before any attempt, or budget stop with empty categories | No | No | No | No | Zero-yield diagnostic |
| `no_eligible_sources` | persisted == 0; `sources_eligible == 0` | No | No | No | No | Zero-yield diagnostic |
| `no_run_scoped_context` | persisted == 0; queue empty and no run context, or attempts == 0 fallback | No | No | No | No | Zero-yield diagnostic |
| `empty_extraction_queue` | persisted == 0; queue empty but sources have run context | No | No | No | No | Zero-yield diagnostic |

Terminal vs non-terminal: the field itself is non-terminal. Workflow terminality is decided by `EvidenceExtractionError` (zero persisted on the main extract path) or later readiness. `mixed_failure` with persisted > 0 does **not** fail the Evidence task.

## 4. Assignment / derivation path

### 4.1 Initialize

`EvidenceExtractionDiagnostics.failure_classification` defaults to `"success"`.

### 4.2 Mutate / derive

Only `EvidenceExtractionDiagnostics.classify(persisted_evidence=..., budget_stop_before_any_attempt=...)` assigns it.

Called once from `EvidenceExtractionService._extract_work_queue` after the queue loop:

```
diagnostics.persisted_evidence = extracted
diagnostics.classify(
    persisted_evidence=extracted,
    budget_stop_before_any_attempt=budget_stop_before_any_attempt,
)
```

### 4.3 Decision table (`classify`)

1. If `persisted_evidence > 0` and not `_has_rejections_or_failures()` → `success`
2. If `persisted_evidence > 0` (any rejection/failure) → `mixed_failure`
3. If `budget_stop_before_any_attempt` → `budget_exhausted_before_evidence`
4. If `sources_eligible == 0` → `no_eligible_sources`
5. If `queue_items == 0` and `sources_with_run_context == 0` → `no_run_scoped_context`
6. If `queue_items == 0` else → `empty_extraction_queue`
7. Build category set from:
   - `extractor_failures` or `extractor_exceptions` → `extractor_failure`
   - `raw_candidates == 0` and attempts > 0 and no exceptions → `no_candidates`
   - `rejected_invalid_or_missing_need_ref` → `invalid_need_refs_all`
   - `rejected_provenance` → `provenance_rejected_all`
   - `rejected_grounding` → `grounding_rejected_all`
8. 0 categories + budget stop + persisted == 0 → `budget_exhausted_before_evidence`
9. 0 categories + attempts == 0 → `no_run_scoped_context`
10. 0 categories else → `no_candidates`
11. 1 category → that value
12. 2+ categories → `mixed_failure`

`_has_rejections_or_failures()` is true if any of:

- `extractor_failures > 0`
- `rejected_invalid_or_missing_need_ref > 0`
- `rejected_provenance > 0`
- `rejected_grounding > 0`
- `rejected_empty_or_invalid_candidate > 0`
- `extractor_exceptions` non-empty

**Not included:** `dedup_hits`, `budget_stop`, `sources_without_evidence`, `inner_calls_exception`, `response_classification_counts`, `valid_empty_result`.

Asymmetry: `rejected_empty_or_invalid_candidate` forces `mixed_failure` when persisted > 0, but has **no** dedicated zero-yield enum value.

### 4.4 Serialize / persist / read

| Location | Role |
|----------|------|
| `EvidenceExtractionDiagnostics.to_dict()` | serializes field |
| `EvidenceExtractionSummary.to_dict()` → `diagnostics` | shared-state payload |

## 5. Response classification vs stage classification

P1-07.6 taxonomy (`incomplete_provider_output`, `empty_provider_output`, `invalid_json`, `root_type_mismatch`, `schema_contract_mismatch`, `valid_empty_result`, `valid_candidates`) lives on inner-chunk `response_shape` and aggregate `response_classification_counts`.

| Question | Answer |
|----------|--------|
| A. Does stage `failure_classification` consume response classifications? | **No.** `classify()` never reads `response_classification` or the counts dict. |
| B. Should it? | Not as a silent merge. They measure different layers. P1-07.6C explicitly kept them separate. |
| C. Was `failure_classification` designed before P1-07.6? | **Yes.** Introduced in P1-07.3 (`95d8a08`, 2026-08-08). P1-07.6 added response taxonomy later. |
| D. Can incomplete_provider_output coexist with stage `success`? | **Yes.** Proven by baseline and CASE E. |
| E. Can 8/8 successful response classes produce `mixed_failure`? | **Yes.** Proven by live `a0eade60` and CASE B. Mechanism: post-extractor candidate rejection. |

### Why incomplete does not become `extractor_failure`

Production wraps `LlmEvidenceExtractor` in `ChunkedEvidenceExtractor`. Inner `EvidenceResponseOutcomeError` is caught, recorded on the inner chunk as `extractor_status=exception`, and **not re-raised**. The wrapper returns `[]` or remaining chunk candidates.

`EvidenceExtractionService` then sees an empty or partial list:

- empty → work-item `extractor_status=no_candidates`, `extractor_failures` unchanged
- non-empty → `extractor_successes += 1`

Inner exceptions therefore do not enter `_has_rejections_or_failures()` unless they escape the chunk wrapper.

## 8. Raw 19 → persisted 16

Two filter layers exist.

### Layer 1 — inside `LlmEvidenceExtractor._build_candidates_from_payload`

Item-contract drops (non-object item, missing/unknown need id, empty statement/excerpt, invalid confidence) happen **before** `raw_candidates` is incremented.

Those drops are visible on `response_shape` (`items_count_pre_filter` / `items_count_post_filter` / `rejected_*`). They are **not** part of 19.

### Layer 2 — `EvidenceExtractionService._extract_from_source`

Every returned candidate takes exactly one path:

| Path | Counter | Counts toward `persisted_evidence`? |
|------|---------|-------------------------------------|
| empty statement/excerpt | `rejected_empty_or_invalid_candidate` | No |
| invalid need refs | `rejected_invalid_or_missing_need_ref` | No |
| other provenance | `rejected_provenance` | No |
| grounding | `rejected_grounding` | No |
| dedup hit | `dedup_hits` | **Yes** (`extracted += 1`) |
| new persist | candidate outcome `persisted` | Yes |

Identity (service layer):

```
raw_candidates
  = persisted_evidence
  + rejected_empty_or_invalid_candidate
  + rejected_invalid_or_missing_need_ref
  + rejected_provenance
  + rejected_grounding
```

Therefore:

```
19 - 16 = 3
  = sum of the four rejection counters
```

`dedup_hits` cannot explain the delta: dedup still increments `persisted_evidence`.

This session does not have the live diagnostics dump for `a0eade60`, so the **split among the four rejection reasons is not locally reconstructable**. That is a **local artifact gap**, not a missing counter. The four counters plus `work_items[].candidate_outcomes[]` already persist in production diagnostics.

## 9. Candidate rejection vs “failure”

For stage `failure_classification`, the following are treated as failures when any evidence also persisted:

- TECHNICAL FAILURE: `extractor_failures` / `extractor_exceptions` (service-visible only)
- DOMAIN REJECTION: grounding, provenance, invalid need refs, empty/invalid candidate

Not treated as failures:

- VALID NEGATIVE RESULT: `valid_empty_result` / empty candidate list
- PARTIAL YIELD via other sources
- DEDUP (counted as persisted)
- Budget cap after successful persists
- Inner incomplete/schema exceptions swallowed by the chunk wrapper

Whether counting domain rejection as `mixed_failure` is “correct” is a naming/product question. The code has treated it that way since P1-07.3 (`test_mixed_failure_classification`: one grounded + one ungrounded → `mixed_failure` with persisted = 1).

## 10. `valid_empty_result` interaction

Zero-candidate successful LLM JSON `{"items":[]}`:

- Inner chunk `extractor_status = success`
- Work-item `extractor_status = no_candidates`
- `extractor_successes` not incremented
- No rejection counters incremented
- Neutral for `_has_rejections_or_failures()`

Alone → stage `no_candidates`.
Alongside persisted evidence → stage `success` (CASE D).
Coexists with live `mixed_failure` only because **other** candidates were rejected, not because empty calls are failures.

## 11. Budget-stop interaction

Common live-desk path: after N successful calls, `_post_source_budget_stop_reason` / `_next_evidence_budget_stop_reason` sets `budget_stop` / `budget_stop_reason` and breaks **without** recording an extractor exception.

If `persisted_evidence > 0`, budget is ignored → `success` unless rejections exist.

Baseline: cap + success.
Live: cap + mixed_failure **because of rejections**, not because of the cap.

Caveat (not the live path): a graceful `BudgetExhaustedError` raised inside `extract()` is `record_exception`'d. That makes `extractor_exceptions` truthy and would force `mixed_failure` even with persisted evidence. Distinct from the pre-call cap check.

## 16. Semantic problems (descriptive, not a mandate to change)

1. **Name vs role:** `failure_classification=mixed_failure` on a completed Evidence task with 16 persisted items looks like a stage failure; it is a partial-yield diagnostic.
2. **Overloaded `mixed_failure`:** (a) persisted > 0 + any rejection; (b) persisted == 0 + multiple categories.
3. **Two layers, one scalar:** provider/response outcome (P1-07.6) vs persist/rejection outcome (P1-07.3) are orthogonal; operators may conflate them.
4. **Inner exceptions are invisible** to the stage field when the chunk wrapper swallows them (explains the baseline “paradox”).
5. **`rejected_empty_or_invalid_candidate` asymmetry** in zero-yield vs partial-yield branches.
6. **`dedup_hits` inflate `persisted_evidence`** relative to unique new rows (not the live 19→16 delta).

These do **not** prove the field is operationally wrong. Downstream does not use it. P1-07.6 did not obsolete it; it added a parallel layer.

## 17. Architectural options (not implemented)

Ranked from repository evidence:

1. **Option A — leave semantics unchanged.** Field is diagnostic-only, test-locked since P1-07.3, unused for control flow. Live `mixed_failure` is consistent with CASE B. Strongest default.
2. **Option D — additive orthogonal diagnostics** (example names only): keep `failure_classification`, optionally expose explicit summaries already implied by existing counters (`response_classification_counts`, rejection counters, `budget_stop_reason`). No rename required.
3. **Option B — rename only.** Would reduce operator confusion; schema/API/docs churn; not justified while the only consumers are dumps and tests.
4. **Option F — deprecate.** Still useful for zero-evidence forensics (`no_candidates`, `grounding_rejected_all`, …). Do not drop.
5. **Option E — derive stage outcome from P1-07.6 classes.** Would hide grounding/provenance partial yield and contradict P1-07.6C. Reject.
6. **Option C — redefine `failure_classification`.** Breaks P1-07.3 tests and operator comparability. Only if a control-flow consumer appears.
