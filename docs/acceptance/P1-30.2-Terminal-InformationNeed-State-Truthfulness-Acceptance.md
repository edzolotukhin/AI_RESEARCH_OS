# P1-30.2 — Terminal InformationNeed State Truthfulness Acceptance

## Executive verdict

**PROPERTY AI: PASS.** Terminal Research readiness is now reconciled per InformationNeed against terminal durable Evidence identity. A completed cached assessment is current only when its existing deterministic sufficiency fingerprint matches the terminal Evidence fingerprint. A newer matching per-IN assessment can no longer be discarded in favor of an older complete aggregate. Unassessed post-assessment Evidence is represented explicitly as stale rather than silently attributed to the prior semantic verdict.

This was an offline implementation and acceptance. No Research, provider call, or LLM call was made.

## Root cause confirmed

The P1-30.1 failure occurred in `ResearchLoopService.run_bounded_loop()`. A partial second Sufficiency pass wrote completed per-IN assessments into `SufficiencyAssessmentCache`; when the downstream reserve stopped the pass, the exception handler applied controlled termination to `previous`, the older complete aggregate. The partial cache survived, but the returned and persisted terminal aggregate ignored it. That produced stale terminal states, including IN3 `MISSING/0` instead of the completed `INSUFFICIENT/2`, and left IN12's 36-Evidence verdict looking current after terminal Evidence reached 41.

## Implemented invariant

At a graceful mid-pass Sufficiency budget stop, terminal aggregation is reconstructed independently for each InformationNeed:

1. Compute deterministic terminal Evidence signals and the existing sufficiency fingerprint.
2. If terminal Evidence is empty, emit a current deterministic `MISSING` assessment.
3. If a completed cached assessment fingerprint matches terminal Evidence, use that assessment as current.
4. If terminal Evidence differs from the last completed assessment, preserve the last semantic status and assessed Evidence count, but mark it `assessment_current=false`, add `stale_evidence`, and expose both assessed and terminal fingerprints/counts.
5. Build ResearchQuestion and run aggregates from those per-IN states, then apply the existing controlled budget termination.

No semantic verdict is invented, promoted, truncated, or reassessed during reconciliation.

## Evidence identity

The implementation reuses `build_sufficiency_assessment_fingerprint()` and `SUFFICIENCY_ASSESSMENT_CONTRACT_VERSION`. Identity includes stable Evidence IDs and canonical persisted Evidence fields plus the InformationNeed, ResearchQuestion, EvidenceExpectation, allowed aspects, and bounded-input contract. Counts alone are never used to claim currency; a same-count/different-Evidence set is stale.

## Before and after semantics

Before:

- partial per-IN updates could be present in the cache;
- reserve exhaustion returned the older complete aggregate;
- a status could be stale even when its displayed label happened to match;
- post-assessment Evidence was not distinguished from assessed Evidence;
- the pending remediation marker and history could remain inconsistent with completed work.

After:

- the terminal aggregate is composed from the latest completed matching per-IN entries;
- `assessment_current` distinguishes current from stale;
- `assessment_evidence_fingerprint` and `terminal_evidence_fingerprint` expose identity;
- `evidence_count` remains the count actually assessed, while `terminal_evidence_count` exposes terminal durable Evidence;
- stale assessments are blocking even if their preserved prior status was `SUFFICIENT`;
- graceful reserve exhaustion remains `COMPLETED/NOT_READY` behavior;
- the completed remediation attempt is recorded, its terminal reconciliation is auditable, and the pending marker is cleared.

## API and UI implications

The existing readiness serialization carries the new bounded fields without a new endpoint, table, or migration. API/UI consumers can distinguish a current verdict from an older verdict over a different Evidence snapshot. `stale_evidence` and the human-readable reason prevent the stale state from being silently collapsed to `MISSING`, `INSUFFICIENT`, or `SUFFICIENT`. Existing status labels remain compatible, and no Evidence text, model trace, credential, or secret is added.
