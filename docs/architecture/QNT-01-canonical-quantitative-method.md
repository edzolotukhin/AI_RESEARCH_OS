# QNT-01 — Canonical Quantitative Research Method

Status: architecture definition, not implementation. Baseline: `cc7d1012ee6a03497e4b43c84121d234ca1569bd` on `acceptance/live-desk-research-01`. Authoritative framework: [CMF-01](CMF-01-canonical-method-framework.md); CMF-02 currently registers Desk only. ARK is accepted and closed. No runtime, schema, migration or provider change is authorized here.

## 1. Current-state audit and preservation

Quantitative is **already a product vertical**, not a blank method. `domain/research_method.py` and project planning select QUANTITATIVE; `api/routers/ui_projects.py` creates project-bound studies; `api/routers/ui_quantitative.py` exposes `/ui/quantitative/studies/{study_id}/{overview,data,analysis,results,report}`. `application/quantitative/ui_service.py`, `vertical_service.py`, `workflow.py` and PostgreSQL quantitative-state repositories implement owner-scoped study state, dataset import, QC/cleaning, weighting, analysis and report progression. Migrations 011/012 protect/project-scope that state. Existing runs and their version semantics are not to be recast.

`DatasetVersion`, `CodebookVersion`, raw/cleaned ancestry, parser/checksum and row/codebook/data fingerprints are defined in `domain/quantitative/dataset.py` and `application/quantitative/fingerprints.py`; importers currently exist for SAV and XLSX. Q1-03/04/05 acceptance records establish byte-to-statistic, cleaning and weighted-view authority. `research_design_authority.py`, `analysis_planning.py`, `analysis_execution.py`, `authority_chain.py`, `finding_lineage.py`, `insight_lineage.py`, `study_sufficiency.py` and `report_composition.py` already provide design-aware execution and result support. The analysis manifest distinguishes mandatory from optional failures. Existing accepted Quant report source is listed by `application/deliverables/service.py` and uses shared PDF/PPTX storage, job, renderer and authorization paths. Quant does **not** have Desk-style report revisions or text-source citations; do not invent them.

CMF-02's actual `application/methods/catalog.py` registers Desk alone. Its `MethodBinding` currently exposes a mandatory `research_adapter() -> MethodAdapter` and Desk-shaped stage labels. Thus `persisted_dataset` is an architectural CMF-01 capability but **not yet a runnable CMF-02 Quant binding**. A narrow typed no-ARK binding/dispatch and dataset-support resolver are implementation prerequisites, not work already done. Preserve legacy Quant activation, routes, accepted report semantics, weighting and historical execution versions while onboarding new opted-in runs.

## 2. V1 user job and bounded product promise

An owner supplies a structured survey dataset plus objective/questionnaire context, inspects imported variables and quality, approves an exact quantitative design and QC/weight policy, executes a finite deterministic plan, inspects traceable statistics and distinct Findings/Insights, accepts a supported report, then requests immutable PDF/PPTX. This is design-aware descriptive survey analysis, **not** an open-ended statistics workbench or causal inference engine. No statistical value is generated by an LLM. Existing screens remain the starting point; new CMF surfaces are capability/authority projections, not a second UI.

## 3. Inputs and dataset authority

The initial CMF Quant V1 uses **existing SAV and XLSX** import. Current UI enforces nonempty files up to 20 MiB; CSV is **not** currently supported and is later scope unless a separate tested importer is approved. XLSX requires explicit sheet selection where ambiguous; parser identity/version and selected sheet belong to import provenance. Preserve file bytes privately, with SHA-256 file checksum and immutable RAW `DatasetVersion`. Do not normalize or overwrite source bytes. `CLEANED` is a new child version tied to approved cleaning decisions, parent fingerprint and retained/excluded respondent lineage. Existing persisted valid datasets may be selected only through project/run-scoped authority checks; they are not implicitly promoted to a new CMF run.

V1 accepts finite, rectangular rows; unique nonempty variable names; recognized categorical, numeric, ordinal, demographic, technical-ID and weight roles. Open text, PII and unsupported variables are not analytically eligible. Missing-value rules and codebook overrides are fingerprinted; invalid rows, duplicate respondent IDs, routing violations and out-of-domain values become explicit QC issues, not silent deletions. Dates are metadata/typed variables only when importer and analysis plan explicitly support them; no automatic time-series interpretation. Encoding, formula/cached-cell behavior, merged/hidden sheets and parser errors must be surfaced rather than guessed. The existing 20 MiB file limit is authoritative; **row/column count ceilings are not established by the inspected UI contract**. Before production CMF rollout, define/test bounded parser limits (rows, columns, cells, decompression, CPU/memory) against representative fixtures; do not claim an arbitrary numeric ceiling is already enforced. A file exceeding a configured bound fails before persistence/analysis, never truncates silently.

Authority chain: original bytes/checksum → immutable DatasetVersion and codebook/schema/data fingerprints → QC assessment/approval and optional approved CLEANED child → approved AnalysisPlan and exact variable/filter/base/weight bindings → deterministic execution manifest and structured result fingerprints → Finding/Insight/report support. Each reported number resolves to dataset version, variables, filter/subpopulation, transformation/cleaning, procedure/version/parameters, unweighted eligible and valid N, denominator, and weight authority/weighted base if applicable. Dataset support is a **tagged dataset authority**, not fabricated `Source` excerpts or Unicode citation spans. Platform-controlled support resolution must fail closed on absent/stale/cross-project refs and must not weaken Desk text-citation checks. No raw respondent/PII payload in ordinary results or telemetry.

## 4. Design, approval and analysis plan

Quant design binds objective and required research questions to an exact dataset/codebook and, when relevant, questionnaire authority; target population/sample description; planned variables and roles (outcome, explanatory/grouping, segmentation); hypotheses only for a declared inferential procedure; filter and base definitions; exclusions; missing-data policy; optional weight policy; requested statistics/comparisons; and limitations. Every planned item has stable requirement IDs and mandatory/optional status. No generic requirement to name a dependent variable for one-way description. Unknown variable, incompatible type, unapproved QC, stale dataset/plan, unsupported procedure or ambiguous weighting mode blocks approval/activation with structured issues. Approval freezes design/input hashes; a changed dataset or plan requires a new version and approval, not silent refresh.

## 5. V1 deterministic procedures

Reuse existing accepted services, do not reimplement their arithmetic. Include: dataset profiling (row/variable counts, type, missingness, unique/category distributions and QC flags); categorical one-way counts/proportions with explicit denominator; numeric count, mean, median, standard deviation, min/max and supported percentiles where the existing `NumericStatisticsService` actually emits them; two-way cross-tab counts and explicitly oriented percentages; existing bounded two-group comparison methods only when their coded preconditions hold; existing NPS/custom-index only with explicit questionnaire/scale/formula authority. An item not implemented by the accepted service is **unsupported**, not synthesized by prose. In particular correlation is deferred unless a deterministic result model and tests are added; regression, clustering, factors, time series, causal/ML analysis are later scope.

Preconditions: numeric summaries require eligible numeric values and valid N; categorical procedures require enumerated valid categories and nonzero denominators; cross-tabs require eligible row/column categories and declared percentage orientation; comparisons require two declared groups, eligible outcome type, method-specific minimum bases/assumptions and explicit alpha/sidedness where inference is supported. Failed assumptions or empty bases yield an inapplicable/insufficient item and limitation, never a fabricated statistic. Outliers are diagnostics/warnings, not automatic deletions. Planned mandatory item failure blocks accepted completion; optional failure remains visible in manifest. Non-significance is a valid result, not an execution failure.

Computation boundary: immutable authority snapshot → deterministic Python services → `StatisticalResult`, `StatisticalTable`, comparison outcome and execution manifest → validated Finding text → Insight interpretation. LLM may help draft design, narratives and review, but cannot create/replace numeric results, denominators, significance, CIs or charts. Narrative claims and displayed numbers must resolve to the persisted result fingerprint; contradictions block acceptance. Reproduction pins computation/parser/policy versions and exact inputs; display rounding never changes authoritative values.

## 6. Weights and statistical integrity

**Weighting is in V1 because it already exists.** Explicit UNWEIGHTED is valid. WEIGHTED requires current approved WeightSet bound to the exact dataset/eligible respondent set and analytical view. Existing embedded or separate keyed imported weights and accepted target-margin weighting remain available only through their own validated approval paths; do not automatically rake or switch modes. Missing, duplicate/unknown-key, negative, nonnumeric or nonfinite weights block; finite zero weights warn, count toward unweighted eligible N and contribute zero weighted base. Zero weighted valid base blocks. Every weighted result shows unweighted N separately from weighted base/effective N where provided; no weighted median/test unless its deterministic implementation and contract support it.

Report per-item total, eligible, nonmissing and group N; numerator/denominator and missingness; weighted base when applicable; filter and exclusion rule. Suppress or warn on small cells according to an explicit versioned disclosure policy before external reporting; do not silently equate suppression with absence of data. Rounding is presentation-only with stated precision and totals caveats. Inferential output may be reported only for a supported procedure with pinned alpha, sidedness, assumptions, uncertainty/CI and multiple-testing policy; no unsupported p-values or blanket significance claims. Association ≠ causation; observational limitations and sampling/representativeness limits remain visible. A sample size is an observed N, not a quality guarantee.

## 7. Readiness, Findings, Insights and review

Quant does **not require ARK** for a supplied dataset. CMF capability is `research_mode=persisted_dataset`, support kind `dataset`; `research_adapter` must become explicitly not-applicable for this mode rather than a fake web-search adapter. No Tavily, Search, text Evidence or Desk sufficiency budget. Optional external context is a future separately governed capability.

Readiness is method-specific and fingerprinted: scoped immutable dataset exists; codebook/QC approval current; required variables/filter/weights available; design/plan approved; planned procedure preconditions met; deterministic mandatory outcomes completed with resolvable provenance. States must distinguish invalid dataset, inadequate valid sample, unsupported analysis, computation/authority failure and successful analysis (including nonsignificance). Missing repository/version is an **operational block**, not “insufficient research.”

Finding = precise, bounded claim supported by one or more persisted statistical result/table/comparison IDs with N/base, method and dataset fingerprint. Insight = interpretation/implication linked to Findings; it cannot alter values, generalize beyond population or imply causality from association. Existing finding/insight lineage and authority-chain validation are binding. Review checks exact source snapshot, variables, filters, QC/cleaning, weight approval, N/denominators, procedure applicability, result values, uncertainty/significance language, limitations and consistency of text/chart/table. Reuse existing Quant accepted-report/approval semantics and shared actor authorization; do not fabricate Desk's draft-report-revision review sequence. A changed report/result creates a separately validated version and cannot retroactively rewrite an accepted source.

## 8. Report, tables, charts and deliverables

Canonical report sections: objective/questions; dataset and population/sample; import/QC and exclusions; design/procedures; key deterministic results and structured tables/charts where actually supported; Findings; Insights; limitations; conclusions. Existing accepted `QuantitativeReportCompositionResult` is the authoritative project source; preserve `qk-1` report source identity and existing source-version/status snapshot semantics. Shared PDF/PPTX services render and store immutable version-bound artifacts; rendering never reruns analysis. Draft/unsupported artifacts must not be labelled accepted. Existing project-level Quant report association does **not** imply that every statistical table/chart is already attached to its PDF/PPTX; any V1 chart/table deliverable path requires explicit source association and renderer acceptance tests.

Minimum table/chart specification references ordered authoritative result IDs/fingerprints; dataset/plan/analysis IDs; variable/category labels, unit, value, N/base, filter/weight status; chart type and axis semantics. Values are copied from deterministic results, never interpolated/generated by LLM or renderer. A chart without complete result provenance is unavailable, not approximated.

## 10. User flow and scope

`/ui/projects` → create/select Quant project → `/ui/quantitative/studies/{id}/overview` → `/data` import/profile/QC/optional weights → `/analysis` design/plan approval and deterministic execution → `/results` Findings/Insights → `/report` accepted report → `/ui/projects/{project_id}/outputs` PDF/PPTX. Existing controls are reused. Genuinely new UI: explicit CMF dataset/design version and analysis-authority visibility if current projections cannot express them; avoid rebuilding whole screens. Owner/project authorization precedes lookup and download.

V1: existing SAV/XLSX survey data, QC/cleaning, optional approved weights, approved design and bounded deterministic descriptive/cross-tab/existing comparison procedures, provenance, supported Findings/Insights/report/export. Later: CSV importer, correlation and broader inference, advanced statistics, time series, richer chart association, optional external context, and any new data modality. Later features need their own deterministic authority and acceptance; they are not implicit in V1.

## 11. Acceptance and implementation sequence

Offline contracts: tiny synthetic SAV/XLSX fixtures with known answers and edge cases (missing/duplicate/PII/zero base/weights/small cell), deterministic fingerprint replay, approved/stale authority, denominator/rounding, no LLM-created number, CMF exact-version/no-ARK contract, Desk/historical compatibility. Integration: owner-scoped import and immutable storage, QC/plan activation, worker restart/version pin, deterministic results and lineage, review/accepted report, PDF/PPTX source binding/repeat download/foreign owner denial. A single separately authorized live case is sufficient **only** for genuinely AI-authored design/narrative behavior; statistical correctness uses known-answer offline fixtures. No Desk-style repeated paid research campaign. Preserve existing Quant acceptance studies as regression evidence, not a substitute for new CMF routing tests.

Implementation increments: (1) dataset authority/ingestion hardening and parser resource bounds; (2) deterministic plan/result contract coverage; (3) CMF persisted-dataset support resolver + Quant registration/opt-in/version pin; (4) Finding/Insight and Quant review binding; (5) existing UI/results projection; (6) accepted report/PDF/PPTX association; (7) focused offline/PG/API/worker integration; (8) minimal separately approved AI live check if needed. Collapse increments when existing code already satisfies them. Do not backfill historical runs or add a migration without a demonstrated persistence need.

## 12. Risks, decisions and real open questions

Decisions: dataset rather than textual Source is authoritative; no ARK for dataset-only V1; preserve weighting; preserve accepted Quant report model; existing SAV/XLSX, not invented CSV; no unimplemented correlation or advanced statistics; strict deterministic arithmetic; fail-closed provenance; opt-in new-run CMF rollout. Risks: workbook decompression/resource abuse, PII leakage in previews, silently stale approvals, overclaiming weighted/inferential results, and assuming report tables/charts are already rendered.

Open implementation questions requiring evidence before rollout: What numeric row/column/cell/decompression limits fit actual local resources and accepted study sizes? Which existing comparison methods and uncertainty outputs meet a documented statistical-review policy? Which structured table/chart associations are presently supported by the project-level Quant report source and renderer? Can the CMF-02 `MethodBinding` be extended with a small typed persisted-dataset branch without breaking Desk pins? These are bounded implementation gates, not permission to weaken CMF integrity or redesign ARK.
