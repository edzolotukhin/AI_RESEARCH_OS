# PRF-06E Project Deliverables handoff

## Source and status

The project catalog reads persisted Desk `Report` revisions from
`ReportQueryService`, verifies their project/run association, and shows the
stored revision number, predecessor, timestamp, title, sections, citations,
registry, and limitations. It never reads the mutable Markdown artifact for
PDF generation. Latest-created and latest-approved are independent pointers.
One exact-report `ReviewResult` with `APPROVE` establishes approval. Missing
review evidence leaves a draft (or an unconfirmed status if the Report itself
claims approval). Multiple or contradictory reviews remain unconfirmed. The
source-version key includes the revision and review-evidence digest, so a later
review creates a new status snapshot without overwriting a draft PDF.

Quantitative reads only accepted, supported
`QuantitativeReportCompositionResult.accepted_report` values from the exact
project/run's immutable state. Composition ID is its version identity; no
Desk revision number or creation time is invented. Claim-unit text and saved
display values are retained. Separate tables/statistics are deliberately not
added without a verified exact-source association. No accepted persisted
report means no catalog item, even for a terminal study.

## Storage and availability

`pdf_deliverables` stores the private completed PDF bytes (`BYTEA`) with
metadata in one PostgreSQL transaction. A unique constraint enforces one
record per project/method/source/version/renderer key. Concurrent insertion
uses `ON CONFLICT DO NOTHING` and returns the winner. A database trigger rejects
updates and deletes of completed records. There is no temporary object/blob
and no metadata-before-blob window; a renderer failure leaves no row. A crash
before commit rolls back the whole row; a retry can generate it. Restarts of
API/worker do not lose committed bytes, subject to normal PostgreSQL durability
and backups. Storage uses no public static path and no extra credentials.
Memory/file backend uses a process-local store for development only and is not
durable across restarts or cross-process deployment.

The render limit is 200,000 source characters, 1,000 rows per directly supplied
table, and 5 MB completed PDF. Font is Debian `fonts-dejavu-core` in the
production Python 3.11 image; ReportLab 4.4.9 is pinned. Rendering does not
fetch remote resources. Download rechecks current project ownership and exact
source/run/study association, then verifies stored size and SHA-256. It returns
server-generated ASCII attachment filenames with private/no-store headers.
Generated bytes are never recomputed during download. Previously generated
draft snapshots remain downloadable after later review, but current catalog
offers a new status-snapshot PDF.

## Deployment and limitations

Apply migration `015_prf06e_pdf` before deploying the new API image. Back up
the PostgreSQL database including `pdf_deliverables`; do not apply an automatic
retention purge. Database byte storage is simple and atomic for the current
5 MB cap, but capacity/backup impact needs operational monitoring before
raising limits. Long-running synchronous PDF requests need timeout and rate
limits at the deployment boundary; production load testing remains to be done.
The existing UI internal-key principal model is unchanged. Action-bound CSRF
tokens protect the new POST; the host deployment must keep the internal key
private and enforce its existing access boundary. No PPTX, preview, DOCX,
cross-method synthesis, or research calculations are introduced.
